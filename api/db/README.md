# Database — plain PostgreSQL, portable forever

The API talks to **standard PostgreSQL** via Prisma. Nothing in the schema or the
application code is tied to a particular host or vendor — moving between managed
Postgres providers, or onto your own server, needs **no application code changes**.

Auth is self-contained too: users live in the `User` table, passwords are bcrypt
hashes, and sessions are our own JWTs. There is no third-party auth provider.

## Connection strings

Two variables, both set in `.env`:

| Variable       | Used for                        | Must be                          |
| -------------- | ------------------------------- | -------------------------------- |
| `DATABASE_URL` | every query the running app makes | pooled connection is fine (`?pgbouncer=true`) |
| `DIRECT_URL`   | `prisma migrate` only             | **non-pooled** — migrations need a real session |

If your Postgres has no connection pooler, set both to the same value.

## What keeps us migration-proof

1. **Versioned SQL migrations** live in `prisma/migrations/**` — generated by
   `npm run migrate`. These files *are* the schema history, committed to the repo.
2. **`db/schema.sql`** — a full DDL snapshot for humans (regenerate with
   `npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script > db/schema.sql`).
3. **`db/backups/latest.sql`** — the most recent full `pg_dump` (schema + data),
   committed so a restorable copy always lives in the repo. Refresh with
   `npm run db:backup`. Schedule it nightly on the server via cron:
   ```
   0 2 * * *  cd /path/to/api && npm run db:backup >> db/backups/cron.log 2>&1
   ```

## Moving to a different Postgres

1. Provision Postgres; create an empty database.
2. Point the API at it: set `DATABASE_URL` and `DIRECT_URL` in `.env`.
3. Apply the schema:  `npm run migrate:deploy`
4. Load the data:  `psql "$DIRECT_URL" < db/backups/latest.sql`
   (or restore just data if the schema already exists).
5. Restart the API.

> Tip: to move BOTH schema and data in one shot, skip step 3 and just restore
> `latest.sql` (a `pg_dump` includes schema). Use `migrate:deploy` when you want
> Prisma's migration table tracked on the new server.

## First-time setup

```
cp .env.example .env         # then fill DATABASE_URL + DIRECT_URL
npm install
npm run migrate:deploy       # creates tables from prisma/migrations
npm run seed                 # admin user + catalog + announcements
npm run dev                  # API on :5000
```
